# 付録C: レビュー・本番導入チェックリスト

ルール・例外のPRレビュー時と、本番投入前の確認事項をまとめました。PRテンプレートや導入手順書にそのまま転用してください。

## C.1 ルール・例外のPRレビュー観点

### 共通

- [ ] 変更の目的がPR説明文に書かれている
- [ ] 変更対象がupstreamルールか自作ルールかが明確（第7章）
- [ ] upstreamルールを触る場合、`override.condition`が`append`か`replace`かが明示され、意図と一致している（第7章）

### ルール追加・変更時

- [ ] `condition`が一行ずつ読める粒度に分解されている（必要ならマクロ化。第3章・第4章）
- [ ] `output`に調査に必要なフィールド（`k8s.ns.name` / `container.image.repository` / `proc.pname` / `proc.cmdline`など）が含まれている
- [ ] 新しいルール名が、既存のupstream/自作ルールと衝突していないか確認した（`falco -V`で検証可能。第7章）
- [ ] テスト環境（tuning-lab相当）で発火・非発火の両方を実測で確認している

### 例外追加時

- [ ] 例外の`name`が、ワークロードと理由が分かる識別子になっている（付録B）
- [ ] キーにしているフィールドが、短命プロセスや起動直後のPodでも解決されるかを確認した（第4章・第6章の「メタデータ解決のrace」）
- [ ] 1〜2フィールドだけの広すぎる例外になっていないか
- [ ] この例外を通り抜けうる攻撃パターンが検討され、第9章の回帰テストで確認されている
- [ ] 対象ワークロードが廃止されたら同じPRで削除される運用が周知されている

## C.2 本番導入前チェックリスト

### ルール設計

- [ ] 有効にするupstreamルールの一覧と、その選定理由を明記している
- [ ] 環境別（開発・ステージング・本番）でルールセットをどう使い分けるかを決めている
- [ ] 新しいルール・チューニングは、まず`priority`をINFORMATIONALに下げて様子を見る運用にしている（第10章）

### CI/CD

- [ ] ルールファイルの変更はGitで管理され、PRを通す（第10章）
- [ ] CIで`falco -V`（構文検証）を実行している
- [ ] CIで第9章の回帰テスト（攻撃シナリオの再生）の少なくとも一部を自動実行している

### 運用

- [ ] 例外の棚卸しの頻度と担当（四半期に1回など）が決まっている
- [ ] 複数クラスタで検証する場合、他クラスタのイベント混入をフィルタする仕組みがある（第2章）
- [ ] upstreamのバージョンアップ時の確認手順（diff取得→overrideの再検証→回帰テスト）が文書化されている（第7章）
