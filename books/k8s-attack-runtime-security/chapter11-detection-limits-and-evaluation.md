# 第11章：Runtime Detectionの限界と評価

## この章で学ぶこと

- 研究C：イベント負荷と検知遅延・イベント欠落の関係（実機検証、かつ重大インシデントの記録）
- CPU/メモリ消費とスケーラビリティのトレードオフ
- Runtime Securityだけでは守れない領域
- 本書全体のまとめ

前章までで「何が検知できるか」を見てきました。本章では視点を変え、**「どれだけ監視を強めても良いわけではない」**という、Runtime Securityの実運用で避けて通れない制約を扱います。

---

## 研究C：イベント負荷と検知遅延の関係

Falcoはすべてのsyscallをカーネルからユーザー空間へ転送し、ルールエンジンで評価します。この処理には当然コストがかかります。本書のラボでは、**実際に負荷を生成してこれを検証しようとし、その過程で想定外の重大なインシデントに遭遇しました**。

![図11-1：イベント負荷と検知遅延の測定パイプライン](/images/fig-ch11-event-pipeline.png)

### インシデント：無制限の負荷生成がDocker Desktop VM全体を無応答にした

最初の負荷生成は、CPU上限を設けずに`while true; do for i in $(seq 1 50); do /bin/true & done; wait; done`という無限ループを投入するものでした。結果、次のことが実際に起きました：

- クラスタのcontrol-planeノードのCPU使用率が**281%**まで上昇
- kube-apiserverへの接続が`TLS handshake timeout`で失敗し、`kubectl`が一切効かなくなった
- **`docker`コマンドそのものが6分以上応答しなくなった**
- ラボのkindクラスタだけでなく、**同じDocker Desktop VM上で動いていた別のkindクラスタすべてに影響**が及んだ

最終的にDocker Desktopの再起動が必要になりました（再起動後、全コンテナは正常に復帰）。

**この事故自体が、研究Cの最も重要な実証結果になりました**。当初想定していた「イベントレートが閾値を超えると検知遅延が徐々に悪化し、イベント欠落が始まる」という**緩やかな劣化モデルは、少なくとも共有リソース環境では成立しませんでした**。実際に起きたのは、**Falcoのイベント欠落検知の仕組みが働く前に、ホストそのものがCPU枯渇で丸ごと無応答になる**という、想定よりずっと急峻で危険な故障モードでした。

### 修正：CPU上限を設けた有界な負荷生成での再測定

教訓を反映し、`resources.limits.cpu: "1"`を設定し、**実行回数が有限**（5000プロセス起動で確実に終了する）負荷生成に変更して再実行しました。

### 実測結果

| 項目 | 値 |
|---|---|
| 観測期間中のイベント数 | 3,371,457件（52秒間） |
| 概算イベントレート | **約65,000 events/sec**（ノード全体） |
| イベント欠落数（`n_drops_total`） | **0** |
| Falco自身のCPU使用率 | 7.5%（アイドル時）→ 13.4%（負荷時） |
| ホスト全体のCPU使用率 | 29.4%（アイドル時）→ 66.6%（負荷時） |

**約65,000 events/secまでは、イベント欠落は一切発生しませんでした。** 当初本文で想定していた「50,000 events/sec前後から欠落が始まる」という数値は架空のものであり、実測ではそれを上回るレートまでmodern eBPFドライバは欠落なく処理できていました。

ただし、**イベント欠落が実際に発生する閾値そのものは、安全に測定することができませんでした**。無制限の負荷生成がホスト全体を無応答にするため、閾値ギリギリを狙った精密な測定は、本ラボのような共有環境では現実的にリスクが高すぎると判断し、それ以上の負荷は加えませんでした。

**考察**: 「イベントレートが閾値を超えると検知遅延が悪化し、イベント欠落が始まる」という段階的な劣化モデルは撤回します。実際に確認できたのは、**「欠落が起きる前に、ホストが丸ごと無応答になる」という、より急峻な故障モード**でした。具体的な数値（遅延ms、欠落率%）は全て架空のものだったため削除し、実測できた範囲の数値（65,000 events/secまで欠落ゼロ）のみを記載します。

**実務上の含意**: 本番環境でFalcoの負荷試験を行う際は、**必ずリソース上限（CPU limit）を設けたうえで、段階的に負荷を上げる**べきです。これは本書が実際に失敗してから学んだ教訓です。無制限の負荷生成は、Falcoだけでなくノード上の他のワークロード、場合によってはクラスタ全体を道連れにするリスクがあります。

## 計測環境の制約

本ラボは4つのkindクラスタが同一のDocker Desktop VMを共有する環境だったため、「純粋に本クラスタの負荷だけによる変化」を正確に切り分けることはできませんでした。負荷試験後もCPU使用率がベースラインに戻りきらなかったのは、他クラスタの並行アクティビティの影響である可能性があります。この点は、専用ノード・専用クラスタでの追試が望ましい領域として残します。

## CPU/メモリ消費とスケーラビリティ

本文執筆時は「ノードあたりのPod数を変化させてFalcoのリソース消費を測定した」という体裁で架空の数値（10 Pods→3%、200 Pods→52%等）を記載していましたが、**この測定は実機では行っていません**。Pod数を変化させた比較検証は、今回のインシデントを踏まえ、より慎重な設計（専用環境、段階的な負荷、厳格なリソース上限）が必要な発展課題として切り出します。

## Runtime Securityだけで守れない領域

ここまでの10章・20本の実験を通して見えてきたのは、Falcoを中心としたRuntime Securityが**「実行時の振る舞いを捉える」という一点において強力な場面がある**一方、次の領域は原理的にカバーできない、あるいは実機検証の結果、本文執筆時の想定より深刻な限界があったということです。

- **構成ミスの予防**（第6章Lab 7、第7章）: 特権コンテナやhostPathの許可自体は、検知ではなくAdmission Controller/Pod Security Standardsで塞ぐべき
- **クラスタ外の攻撃対象領域**（第4章Lab 3）: ただし現在のKubernetesデフォルトでは、この経路自体がすでに塞がれていることも判明した
- **複数データソースをまたぐ相関**（第10章）: データソースを足しても、相関キーが境界ごとに変わるため自動的には繋がらない
- **パケット内容・頻度に基づく検知**（第8章Lab 13、第9章Lab 17b）: ポートスキャンやDNS exfiltrationは、Falcoのアーキテクチャ上そもそも検知できない
- **高負荷時の確実性**（本章）: 段階的な劣化ではなく、ホスト全体が道連れになる急峻な故障モードがある

Runtime Securityは「最後の砦」ですが、**唯一の砦ではありません**。イメージスキャン、Admission Control、RBAC設計、クラウドIAMの最小権限化といった事前防御と組み合わせて初めて、本書で示した攻撃に対する現実的な防御態勢が組めます。

## 本書のまとめ

1. **攻撃者視点で見ると、Kubernetesには「ノード内」「APIサーバ」「クラウドAPI」という3つの異なる境界線がある**（第1章）
2. **攻撃が成立した15シナリオのうち、標準ルールだけの検知率は33%、カスタムルールを加えても約80%にとどまり、2本は原理的に検知不可能だった**（第10章・研究A、実機ベースの数値）
3. **syscallだけでは攻撃チェーン全体を追跡できず、しかもデータソースを足すだけでは解決しない——相関キーが境界ごとに変わるという、より深い問題がある**（第10章・研究B）
4. **監視の負荷試験には重大な事故リスクがあり、段階的な劣化ではなくホスト全体を巻き込む急峻な故障が起こり得る**（第11章・研究C）
5. **本文執筆時に引用した標準Falcoルールの多くが実在しなかった**——これは本書全体を通じた、おそらく最も重要な教訓である

前作『Falco実践シリーズ』が「どう使うか」を扱ったのに対し、本書は「使ってみた結果、どこまで見え、どこが見えないのか」を実験で確かめようとしました。結果として分かったのは、**最初に書いた原稿の多くが、実機で検証する前の"もっともらしい想定"に過ぎなかった**ということです。実験コードと実測ログはすべて[k8s-attack-runtime-security-lab](https://github.com/keitahigaki-prog/k8s-attack-runtime-security-lab)で公開しており、再現・追試を歓迎します。

次に手を伸ばすとすれば、**専用の、他クラスタと資源を共有しない環境での研究Cの追試**、そして**実クラウド環境・Calico等の高機能CNIを使った、第9・10章の未検証部分の補完**になるでしょう。それはまた別の機会に。
