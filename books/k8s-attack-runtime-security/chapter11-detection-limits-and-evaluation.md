# 第11章：Runtime Detectionの限界と評価

## この章で学ぶこと

- 研究C：イベント負荷と検知遅延・イベント欠落の関係
- CPU/メモリ消費とスケーラビリティのトレードオフ
- Runtime Securityだけでは守れない領域
- 本書全体のまとめ

前章までで「何が検知できるか」を見てきました。本章では視点を変え、**「どれだけ監視を強めても良いわけではない」**という、Runtime Securityの実運用で避けて通れない制約を扱います。

---

## 研究C：イベント負荷と検知遅延の関係

Falcoはすべてのsyscallをカーネルからユーザー空間へ転送し、ルールエンジンで評価します。この処理には当然コストがかかります。本書のラボでは、**人工的にイベント量を変化させ、検知遅延がどう変わるかを測定**しました。

![図11-1：イベント負荷と検知遅延の測定パイプライン](/images/fig-ch11-event-pipeline.png)

### 測定結果（イベント生成レート別の検知遅延）

| イベント生成レート | 検知遅延（中央値） | 検知遅延（p99） | イベント欠落率 |
|---|---|---|---|
| 1,000 events/sec | 12ms | 45ms | 0% |
| 10,000 events/sec | 38ms | 210ms | 0% |
| 50,000 events/sec | 180ms | 1,850ms | 0.3% |
| 100,000 events/sec | 420ms | 4,200ms | 4.7% |

**考察**: イベントレートが一定の閾値（このラボ構成ではおおよそ50,000 events/sec前後）を超えると、**検知遅延が非線形に悪化し、イベント欠落も発生し始めます**。これは、eBPFのring bufferがオーバーフローし、カーネル側でイベントがドロップされるためです。ドロップされたイベントは、Falcoのメトリクス（`falco.n_evts_dropped`等）で確認できますが、**ドロップされたイベントの中に重大な攻撃の痕跡が含まれていても、それを後から知る術はありません**。

**実務上の含意**: 高負荷なワークロード（大量のバッチジョブ、ビルドパイプラインなど）が同居するノードでは、**Falcoのルール数を絞る／不要なイベント種別をフィルタする**ことで、イベント生成量そのものを抑える設計が必要になります。「全部見る」ことと「確実に見る」ことはトレードオフの関係にあります。

## イベント欠落の発生条件

欠落が起きる条件をさらに切り分けると、次の3つに整理できました。

| 欠落の原因 | 発生条件 | 対策 |
|---|---|---|
| ring bufferのオーバーフロー | 瞬間的なイベントバースト | バッファサイズの調整（`buf_size_preset`） |
| ルール評価のボトルネック | 複雑な条件式を持つルールが多数登録されている | ルールの簡素化・優先度の見直し |
| 出力側のバックプレッシャー | Falcosidekick等の出力先が詰まっている | 非同期化・バッファリングの導入 |

第3章で触れた「`buf_size_preset`はバーストにだけ効く」という前提は、この章の実験で改めて裏付けられました。**定常的な高負荷にはバッファサイズでは対応できず、ルール自体を絞る必要があります。**

## CPU/メモリ消費とスケーラビリティ

ノードあたりのワークロード数（Pod数）を変化させ、Falcoプロセスのリソース消費を測定しました。

| ノード上のPod数 | Falco CPU使用率 | Falcoメモリ使用量 |
|---|---|---|
| 10 Pods | 3% | 180MB |
| 50 Pods | 11% | 320MB |
| 100 Pods | 24% | 480MB |
| 200 Pods | 52% | 810MB |

Pod数の増加に対して、CPU使用率はほぼ線形に増加しました。これは**syscall発生量がPod数にほぼ比例する**ためで、特別な異常ではありません。ただし、**200 Pods規模のノードでCPU使用率が50%を超える**という結果は、他のワークロードと同居させる上で無視できないコストです。

**考察**: 「とりあえず全ノードにFalcoを入れる」という判断は妥当ですが、**高密度ノード（Pod数が多いノード）では、ルールセットの最適化やサンプリングの検討が必要**になります。本書のラボ規模（数十Pod程度）では問題になりませんが、本番の大規模クラスタでは必ず負荷試験を行うべきです。

## Runtime Securityだけで守れない領域

ここまでの10章を通して見えてきたのは、Falcoを中心としたRuntime Securityが**「実行時の振る舞いを捉える」という一点において非常に強力**である一方、次の領域は原理的にカバーできないということです。

- **構成ミスの予防**（第6章Lab 7、第7章）: 特権コンテナやhostPathの許可自体は、検知ではなくAdmission Controller/Pod Security Standardsで塞ぐべき
- **クラスタ外の攻撃対象領域**（第4章Lab 3）: kubelet APIのような、ノード内でもAPIサーバ経由でもない独立した領域
- **複数データソースをまたぐ相関**（第10章）: syscallだけでは攻撃チェーン全体を再構築できない
- **高負荷時の確実性**（本章）: イベントレートが一定を超えると検知自体が揺らぐ

Runtime Securityは「最後の砦」ですが、**唯一の砦ではありません**。イメージスキャン、Admission Control、RBAC設計、クラウドIAMの最小権限化といった事前防御と組み合わせて初めて、本書で示した20シナリオのような攻撃に対する現実的な防御態勢が組めます。

## 本書のまとめ

1. **攻撃者視点で見ると、Kubernetesには「ノード内」「APIサーバ」「クラウドAPI」という3つの異なる境界線がある**（第1章）
2. **20シナリオの実験で、標準ルールだけの検知率は40%、カスタムルールを加えても70%にとどまった**（第10章・研究A）
3. **syscallだけでは攻撃チェーン全体を追跡できず、Audit Logs・クラウドAudit Trail・ネットワーク観測との統合が必須**（第10章・研究B）
4. **監視を強めるほど、検知遅延・イベント欠落・リソース消費というコストが非線形に増える**（第11章・研究C）

前作『Falco実践シリーズ』が「どう使うか」を扱ったのに対し、本書は「使ってみた結果、どこまで見え、どこが見えないのか」を実験で確かめました。次に手を伸ばすとすれば、**今回の実験ラボをより大規模なクラスタで再現し、研究Cの閾値が実運用規模でどう変化するか**を検証することになるでしょう。それはまた別の機会に。
